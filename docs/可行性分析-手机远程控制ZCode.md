# 可行性分析：手机 App → 自建服务器 → ZCode 插件 → 远程布置任务

日期：2026-11-04 ｜ 结论先行：**总体可行（推荐做）**，核心链路全部能用 ZCode 官方扩展点实现；唯一的硬边界是"客户端完全空闲/关闭时无法即时唤醒"，有可接受的兜底方案。

---

## 1. 目标拆解

- 手机能向 ZCode 客户端下发任务（对话式布置）
- 数据经用户自己的服务器中转（手机和 PC 不直连）
- PC 上的 ZCode 模型执行任务、操作电脑，进度/结果回传手机

## 2. 总体架构

```
┌─ 手机 Android App ──┐        ┌─ 你的服务器（VPS）──┐        ┌─ PC：ZCode Desktop ─────────┐
│ 发任务 / 看进度     │ HTTPS/ │  REST + WebSocket   │ WSS/   │ 插件（一个插件三合一）：      │
│ 批准敏感操作 / 收推送│ ←────→ │  SQLite 任务队列     │ ←────→ │  · MCP server = 桥接进程     │
└────────────────────┘  WSS   │  设备配对 / 推送     │ 长轮询  │  · Hooks = 任务注入+远程批准 │
                              └────────────────────┘        │  · ZCode 模型 → 操作电脑     │
                                                            └─────────────────────────────┘
```

PC 端始终**主动外连**服务器（WS 长连接），无需公网 IP、无需端口映射。手机只跟服务器说话。

## 3. 关键机制验证（基于本机 ZCode 实际调研，非猜测）

调研了本机插件清单规范、hooks 文档、MCP 配置格式，确认以下扩展点全部真实可用：

| ZCode 能力 | 用途 | 状态 |
|---|---|---|
| 插件 MCP server（`.mcp.json`，子进程常驻） | 桥接进程：WS 连你的服务器收任务；同时向模型暴露工具 | ✅ 已验证格式 |
| MCP 工具（如 `remote_fetch_tasks` / `remote_report`） | 模型"拉取"手机下发的任务、回传结果 | ✅ 已验证格式 |
| `Stop` hook（可请求继续，至多 3 次） | 会话空转时若有新任务 → 注入上下文唤醒模型执行 | ✅ 官方文档确认 |
| `SessionStart` hook（`additionalContext` 注入） | 客户端启动时播报服务器上积压的任务 | ✅ 官方文档确认 |
| `PermissionRequest` hook（可返回 allow/deny） | **远程批准**：敏感操作权限请求转发到手机，hook 长轮询等你点"允许" | ✅ 官方文档确认 |
| `PostToolUse` hook | 把执行动作流式回显到手机（"正在编辑 xx 文件…"） | ✅ 官方文档确认 |
| 插件用户配置（`user_config.*`） | 服务器地址、token 在设置界面填写，不写死 | ✅ 已验证格式 |
| 无头 CLI / 外部注入用户消息 API | 让 PC 从"完全没开会话"状态被唤醒 | ❌ 不存在（Desktop 用户无全局 `zcode` CLI，config 中也无内置远程功能） |

**核心工作闭环**：桥接进程收到手机任务 → `Stop`/`SessionStart` hook 注入"有待办任务" → 模型调用 MCP 工具取出任务原文 → 像正常对话一样执行并操作电脑 → 通过 MCP 工具回传进度/结果 → 服务器推送手机。

## 4. 三个组件设计要点

### 4.1 ZCode 插件（PC 端，工作量核心）
- **MCP server（node 进程）**：会话期间常驻；启动即连服务器 WS；注册 3 个工具：`remote_fetch_tasks`（取任务+确认消费）、`remote_report`（进度/结果上报）、`remote_status`（查询在线状态）
- **Hooks**（`hooks/hooks.json`，用 `type:"process"` 避开 Windows shell 兼容问题）：
  - `Stop`：查本地队列，有任务则 `additionalContext` + 请求继续（注意 3 次上限，见 §5）
  - `SessionStart`：播报积压任务
  - `PermissionRequest`：转发权限请求到服务器，长轮询手机端决定（可配置白名单自动放行）
- 服务器地址/token 走 `user_config`；本地队列文件做断线缓冲

### 4.2 服务器（你的 VPS）
- 单服务即可：Node.js（Fastify/Express）或 Go；REST（发任务/查状态）+ WebSocket（双端长连接）+ SQLite
- 设备配对：PC 端生成一次性配对码 → 手机输入绑定，颁发设备 token
- 任务模型：`{id, text, workspace, ts, state: queued/running/done/failed, output_tail[]}`
- 需要：公网可达 + HTTPS（域名+证书；内网则用 frp 穿透）

### 4.3 Android App
- 推荐：**Kotlin + Jetpack Compose 原生**（发任务、任务列表、详情回显、批准弹窗、前台服务保活 WS）
- 更省事的替代：先做 H5 网页 + WebView 壳 App（1 天内出原型，后续再原生化）
- 推送：不用 FCM（国内不可靠）；前台服务 + 自建 WS，或退化为通知栏常驻+拉取

## 5. 能力边界与风险（必读）

1. **空闲唤醒受限（唯一硬边界）**：`Stop` hook 的"请求继续"上限 3 次；客户端完全没开会话时无法被外部唤醒。兜底：开机自启 ZCode Desktop（SessionStart hook 会播报积压任务）；保持一个"值守会话"是最顺滑用法。若未来 ZCode 开放 CLI/无头模式，可无痛升级为全时唤醒。
2. **客户端关闭 = 桥接停止**：任务会堆积在服务器端，下次开会话自动补发，不丢。
3. **远程无人值守的权限问题**：模型执行中请求工具权限时，要么手机上点批准（安全、有打断），要么把该 workspace 权限预设为自动批准（顺畅、风险高）——做成插件里的分级开关。
4. **安全**：token 认证 + 配对码绑定；全程 TLS；**任务注入 ≈ 任意代码执行**，务必启用"敏感操作需手机批准"白名单机制；你的服务器能看到明文任务，可选端到端加密（手机/PC 共享密钥，服务器只存密文）作为二期。
5. **国产 ROM 杀后台**：安卓端用前台服务 + 通知栏常驻。
6. 任务注入需幂等（队列 + 去重），防止重连后重复执行。

## 6. 分期实施与工作量

| 阶段 | 内容 | 工时 |
|---|---|---|
| M1 | 服务器：REST+WS+SQLite+配对码 | 0.5–1 天 |
| M2 | 插件：MCP 桥 + 3 工具 + Stop/SessionStart hook + 本地市场安装 | 1–2 天 |
| M3 | Android 最小版：配对、发任务、任务列表状态 | 1–2 天 |
| M4 | 打磨：远程批准、执行回显推送、自启、（可选）E2E 加密 | 2–3 天 |

**MVP（M1–M3）约 3–5 天可达"手机发任务 → PC 的 ZCode 执行 → 手机看结果"。**
